# 大音频分块无缝播放

稽木世界（gitblock.cn）限制单个资源不能超过 8 MB，超过这个大小的音频不能整个上传。

以往多数音频分块播放的作品，在不同音频块衔接时会卡一下，也就是有一小段时间完全没有声音。

而这个作品做到了**无缝衔接**，每一块的音质也和原文件一致。

做法是用 FFmpeg 把音频从 0 秒起每满一分钟切一块，直到切完（当前这首切成 8 块，最大的约 3.7 MB，远低于限额）：音乐段默认按 `input.mp3` 自己的码率重新编码（这首是 320 kbps；输入码率更低时输出也会相应降低，不会白撑体积），前面那几分钟用于对时的静音则用 32 kbps 的静音帧填充。分块上传后在 Scratch 里同时播放。

## 目录结构

```
.
├─ input.mp3                  # 待处理的整曲（脚本只认这个文件名）
├─ split.py                   # 切块 + 编码
├─ duration.py                # 读音频时长（秒）
├─ output-chunks/             # 切块结果：0.mp3、1.mp3、…
│  └─ 0.mp3 … 7.mp3
├─ temp/                      # 中间文件（运行成功后会自动删除）
│  ├─ source.wav              # 整曲解码后的 PCM
│  ├─ silence.mp3             # 用来填静音的 32 kbps 静音帧
│  └─ wav/                    # 每块的 WAV（带前导静音）
├─ 大音频分块无缝播放.sb3
└─ README.md
```

## 环境要求

- Python 3.8+，只用标准库，无需 `pip install`
- `ffmpeg` 和 `ffprobe` 在 `PATH` 里（需带 `libmp3lame` 编码器，gyan.dev 的 full build 即可）

验证：

```powershell
ffmpeg -version
ffprobe -version
python --version
```

## 快速开始

在项目目录下：

```powershell
# 1) 看整曲多长（秒），填到 .sb3 里
python duration.py

# 2) 切块并编码，输出到 output-chunks/
python split.py
```

`split.py` 跑完会打印每一块的时长、体积和校验结果，最后一行是 `总体: 通过` 或 `总体: 有问题`；跑成功后 `temp/` 里的中间文件会被自动清掉。

以当前这首 473.125 秒的曲子为例（`SECONDS_PER_CHUNK = 60`）：切出 8 块，前 7 块各 60 秒，第 8 块 53.125 秒；合计约 24.5 MB，最大一块 3.66 MB。

## split.py

### 调用

```powershell
python split.py                                        # 全部用默认配置
python split.py -i 另一首.mp3                           # 换源文件
python split.py -s 30 -b 256k -o out2                   # 每块 30 秒、256 kbps、输出到 out2
python split.py --help                                 # 查看全部参数
```

所有配置都能用命令行参数覆盖（相对路径按脚本所在目录解析）；不传参数时用文件顶部「配置区」的默认值：

| 参数 | 对应常量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `-i, --input` | `SRC` | `input.mp3` | 源文件 |
| `-o, --output-dir` | `OUT_DIR` | `output-chunks` | 输出目录，不存在会自动创建 |
| `-t, --temp-dir` | `TEMP_DIR` | `temp` | 中间文件目录 |
| `-s, --seconds-per-chunk` | `SECONDS_PER_CHUNK` | `60` | 每块秒数；改这个值要同步改 `.sb3`。60 秒在 320 kbps 下约 2.4 MB 音乐 + 每分钟 0.24 MB 静音，最大一块约 3.7 MB，给 8 MB 限额留足余量 |
| `--name-fmt` | `NAME_FMT` | `{0}.mp3` | 输出文件名格式，`{0}` 是序号 |
| `-b, --music-bitrate` | `MUSIC_BITRATE` | `auto` | 音乐段码率；`auto` = 按输入文件自动决定（MP3 用它自己的码率，其它格式用 320k）。也可以写 `320k` / `192k` 强制指定 |
| `--silence-bitrate` | `SILENCE_BITRATE` | `32k` | 前导静音码率，MPEG-1 立体声的最低值，只影响体积，不影响音质 |

采样率固定 44.1 kHz、双声道、16 bit。

### 它做了这些事

1. **解码一次**：`input.mp3` → `temp/source.wav`（PCM），后面全部基于这份 PCM，不再碰原 MP3。
2. **每分钟切一块**：从 0 秒起按 `SECONDS_PER_CHUNK`（默认 60 秒）切，直到切完；第 *n* 块 = 前 *n* 分钟静音 + 第 *n* 分钟的音乐，写到 `temp/wav/n.wav`。切点落在采样点上（60 × 44100），没有帧边界误差。
3. **逐块独立编码**：每块单独用 LAME CBR 编码成 `output-chunks/n.mp3`，码率按 `MUSIC_BITRATE`（默认 `auto`：MP3 输入用输入码率，其它格式用 320k）；编码时加 `-reservoir 0` 关掉比特池，让每一帧都能独立解码；同时保留 LAME 写的 Xing/Info 标签，解码器据此裁掉编码器延迟，所以每块解码出来就是精确的 PCM 长度。
4. **把长静音换成低码率帧**：编码完成后，把前导静音里「整帧都落在静音区」的那些帧，替换成预先生成好的 32 kbps 静音帧（帧数不变，前后各留了余量）。静音部分不再按音乐段的码率算，而是固定 32 kbps，解码结果分毫不变。
5. **回读校验**：把每块解码回 PCM，检查采样数是否精确等于期望值、静音段是否全零、音乐段和源 PCM 的误差（SNR），并打印每块体积和总体结论。
6. **清理缓存**：中间文件用不着了就马上删——`source.wav` 切完块就删，每块的 WAV 编码完就删，静音帧全部编码完一起删；最后 `temp/` 空了就把 `temp/` 文件夹也删掉。中途出错时，还没用到的缓存会留在 `temp/` 里，方便排查/重跑。

### 音质和码率是怎么自动决定的

`MUSIC_BITRATE` 默认是 `auto`。编码前先用 ffprobe + 帧扫描看一眼输入：

- 输入是 **MP3**：CBR 用它的码率，VBR 用平均码率，取最接近的标准档。比如输入 320k → 输出 320k，输入 128k → 输出 128k。
- 输入**不是 MP3**（WAV/FLAC/ALAC 等无损格式，或 OGG 等）：统一用 320k（MP3 能给的最高档）。
- 想强制某个码率：`-b 320k` / `-b 192k`。

所以低码率输入不会再被 320k 白白撑大：128k 的输入切成 8 块合计约 13.6 MB，而不是 24.5 MB。

注意：分块必须重新编码，所以码率跟输入一样也会多一代 MP3 损失。实测把 128k 源再编码成 128k，和源 PCM 的误差约 22 dB SNR（细听能分出比原文件糊一点）；再编码成 320k 则是 42 dB（基本透明），但体积是 2.5 倍。想尽量保音质、不在乎体积时，用 `-b 320k`。

另外两点没变：

- MP3 是有损格式，**不可能逐字节无损**。真正无损只能用 WAV/FLAC，而 60 秒立体声 WAV 就超过 10 MB，会超过 8 MB 的上传限制。
- 也没有采用「直接切原 MP3 字节」的写法：MP3 每帧都依赖前面的帧（比特池 + 合成滤波器），从中间硬切会让每块开头出现约 26 ms 的凹陷，那正是这个作品要避免的。重新编码一次是保证无缝的必要代价。

### 为什么静音几乎不占体积

如果前导静音也按音乐段的码率编码，第 8 块光静音就有好几 MB（音乐 320k 时是 16 MB 以上），直接超限。

LAME 默认会跨帧共用比特（比特池），一帧的数据可能引用前面几帧的字节，这种流没法从中间替换帧。这里用 `-reservoir 0` 编码，使每一帧都自包含，于是可以把前面几分钟静音的帧整段换成 32 kbps 的静音帧：帧数不变，解码后的采样数和音乐起点也分毫不变，静音部分固定只按 32 kbps 算（每分钟 0.24 MB）。

### 为什么这样能无缝

MP3 每帧的频谱数据依赖前面几帧（比特池）。直接按字节切原 MP3，每块开头都会缺前文，产生约 26 ms 的凹陷。这里的每块都是从 PCM 独立编码出的新文件，第一帧不依赖任何前文；编码器把延迟/填充写进了 LAME 标签，解码器会自动裁掉，所以每块解码出来就是精确的 PCM 长度。

替换静音帧只发生在音乐开始之前（后面还留了至少 2 帧原编码的静音），而解码器在静音区的内部状态本来就是全零，所以无论换成什么样的低码率静音帧，音乐部分都逐采样不变。

### 在 Scratch 里怎么用

每块前面都垫了「序号 × 每块秒数」的静音，因此可以把 8 个声音**同时**开始播放：第 *n* 块要等 *n* × 每块秒数（默认每块 60 秒）才出声，任意时刻只有一块真正在响。这样就不依赖 Scratch 的定时器和「等待」精度，块与块之间也不会出现空隙。

换歌只需替换 `input.mp3` 后重跑 `split.py`，再用 `duration.py` 读出新的总时长填回 `.sb3` 的 `计时器 < …` 判断；如果时长变了导致块数变化，记得在 `.sb3` 里同步增加/删除声音和对应逻辑。改了 `split.py` 之后，`.sb3` 里嵌的还是旧音频，需要把 `output-chunks/` 里的新文件重新导入、替换掉对应的 8 个声音。

## duration.py

### 用途

看 `input.mp3` 有多长（秒），把输出的数字填到 `.sb3` 里——作品里用 `计时器 < 时长` 判断什么时候播完。

### 调用

```powershell
python duration.py                 # 默认读同目录的 input.mp3
python duration.py 别的文件.mp3     # 也可以读别的文件
```

输出秒数，保留三位小数，例如 `473.125`，直接抄进 `.sb3` 就行。

### 为什么不用 ffprobe 直接看

`ffprobe` 对没有时长索引的 MP3 会按首帧码率估算，可能差出好几秒。脚本会把它和「数 MPEG-1 Layer III 帧数 × 1152 / 采样率」的结果对一下，差超过 0.5 秒就用数帧的准确值，所以输出的数字可以直接用。

## 常见问题

- **`找不到源文件: …/input.mp3`**：确认源文件就叫 `input.mp3`，且和脚本在同一目录。
- **`命令失败: ffmpeg …`**：多半是 `ffmpeg` 不在 `PATH`，或输出文件被别的程序占用。
- **块数和 `.sb3` 对不上**：改 `SECONDS_PER_CHUNK` 或换了更长的歌之后，`sb3` 里的声音数量要一起改。
- **输入是 128k 的 MP3，输出也会是 128k 吗？**：默认就是这样（`MUSIC_BITRATE = "auto"` 会按输入码率决定）。想不管输入、强制高码率就用 `python split.py -b 320k`。
- **想省空间**：跑成功后 `temp/` 会被自动清掉，不用手动删；默认已经按输入码率编码，低码率输入不会白撑体积。想再小可以手动 `-b 192k`（音质会明显变差）。
- **想换每块长度 / 码率又不想改代码**：直接用命令行参数，例如 `python split.py -s 30 -b 256k`；参数表见上面的「调用」。
