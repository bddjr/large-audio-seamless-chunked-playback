# 大音频分块无缝播放

稽木世界（gitblock.cn）限制单个资源不能超过 8 MiB，超过这个大小的音频不能整个上传。（参考 https://github.com/a49594a/scratch-gui/blob/c2c14c6895901bc04c8c1ab197f328099cf5ae8e/src/lib/project-saver-hoc.jsx#L226 ）

以往多数音频分块播放的作品，在不同音频块衔接时会卡一下，也就是有一小段时间完全没有声音。

而这个作品做到了**无缝衔接**，每一块的音质也和原文件一致。

做法是用 FFmpeg 从后往前切块，每块不超过 8 MiB（这首 320k 切成 3.52 + 8.00 + 8.00 MiB）。音乐段按输入码率编码，前导静音用 32 kbps 静音帧填充；分块后在 Scratch 里同时播放。

## 目录结构

```
.
├─ input.mp3                  # 待处理的整曲（脚本只认这个文件名）
├─ split.py                   # 切块 + 编码
├─ duration.py                # 读音频时长（秒）
├─ output-chunks/             # 切块结果：1.mp3、2.mp3、…
│  └─ 1.mp3 …（数量按大小自动决定，这首 3 块）
├─ output-chunks-duration.txt # 每块时长（给 Scratch 列表导入用）
├─ COPYING                    # 许可证（代码是 Unlicense；input.mp3 版权不属于本项目）
├─ 大音频分块无缝播放.sb3
└─ README.md
```

## 环境要求

- Python 3.8+，只用标准库，无需 `pip install`
- `ffmpeg` 和 `ffprobe` 在 `PATH` 里（需带 `libmp3lame` 编码器，gyan.dev 的 full build 即可）

验证：

```powershell
ffmpeg -version
ffprobe -version
python --version
```

## 快速开始

在项目目录下：

```powershell
# 1) 看整曲多长（秒），填到 .sb3 里
python duration.py

# 2) 切块并编码，输出到 output-chunks/
python split.py
```

`split.py` 跑完会打印每一块的时间范围、体积和填充率，以及校验结果，最后一行是 `总体: 通过` 或 `总体: 有问题`（有问题时退出码为 1）。每次开始前会把输出目录整个删掉重建；试编码时会临时用输出目录里的 `_trial.mp3`，跑完就删。

以当前这首 473.125 秒、320 kbps 的曲子为例（默认 8 MiB）：切出 3 块——0–92.209 秒、92.209–292.626 秒、292.626–473.125 秒；体积 3.52 + 8.00 + 8.00 MiB，合计约 19.5 MiB。第一块不满是正常的：它是从后往前填满后剩下的。

## split.py

### 调用

```powershell
python split.py                                        # 默认按 8 MiB 从后往前填满
python split.py --max-size 4M                          # 每块不超过 4 MiB
python split.py -s 60                                  # 旧行为：每块固定 60 秒
python split.py -i 另一首.mp3 -b 256k -o out2           # 换源文件、码率、输出目录
python split.py --help                                 # 查看全部参数
```

所有配置都能用命令行参数覆盖（相对路径按脚本所在目录解析）；不传参数时用文件顶部「配置区」的默认值：

| 参数 | 对应常量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `-i, --input` | `SRC` | `input.mp3` | 源文件 |
| `-o, --output-dir` | `OUT_DIR` | `output-chunks` | 输出目录；**开始前会整个删掉重建**，不存在会自动创建 |
| `--max-size` | `MAX_CHUNK_BYTES` | `8MiB` | 每块体积上限，可以写 `8M` / `8MiB` / `8388608`；不填 `-s` 时按它从后往前填满每块，填了 `-s` 时只用于超限检查 |
| `-s, --seconds-per-chunk` | `SECONDS_PER_CHUNK` | 不填 | 填了就按固定秒数切块（优先于 `--max-size`），块体积超上限会被判 BAD |
| `--name-fmt` | `NAME_FMT` | `{0}.mp3` | 输出文件名格式，`{0}` 是序号，从 1 开始 |
| `-b, --music-bitrate` | `MUSIC_BITRATE` | `auto` | 音乐段码率；`auto` = 按输入文件自动决定（MP3 用它自己的码率，其它格式用 320k）。也可以写 `320k` / `192k` 强制指定 |
| `--silence-bitrate` | `SILENCE_BITRATE` | `32k` | 前导静音码率，MPEG-1 立体声的最低值，只影响体积，不影响音质 |
| `--duration-file` | `DURATION_FILE` | `output-chunks-duration.txt` | 每块时长列表的输出文件，一行一个、LF 换行 |

采样率固定 44.1 kHz、双声道、16 bit。

### 它做了这些事

1. **清空输出目录**：开始前把输出目录整个删掉再重建（子目录也会没），保证里面是空的，避免上次的块或半成品混进来。
2. **解码一次**：`input.mp3` 通过 ffmpeg 管道直接读成内存里的 PCM（不落 WAV），后面全部基于这份 PCM，不再碰原音频。
3. **从后往前逐块填满**：默认先试编码最后一块，找到「不超过 `MAX_CHUNK_BYTES`」的最长音乐，再以它的起点为终点填上一块，一直往前推到第一块。这样前面的块尽量短，静音总量和总体积最小；第一块是剩下的，可能偏小。试编码临时写在输出目录的 `_trial.mp3`，规划完删除。边界确定后把每块的总时长写到 `output-chunks-duration.txt`（一行一个，LF 换行）。
4. **逐块独立编码**：每块单独用 LAME CBR 编码成 `output-chunks/n.mp3`（n 从 1 开始），码率按 `MUSIC_BITRATE`（默认 `auto`：MP3 输入用输入码率，其它格式用 320k）；编码时加 `-reservoir 0` 关掉比特池，让每一帧都能独立解码；同时保留 LAME 写的 Xing/Info 标签，解码器据此裁掉编码器延迟，所以每块解码出来就是精确的 PCM 长度。
5. **把长静音换成低码率帧**：编码完成后，把前导静音里「整帧都落在静音区」的那些帧，替换成预先生成好的 32 kbps 静音帧（帧数不变，前后各留了余量）。静音部分固定只按 32 kbps 算，解码结果分毫不变。
6. **回读校验**：把每块解码回 PCM，检查采样数是否精确等于期望值、静音段是否全零、音乐段和源 PCM 的误差（SNR）、体积是否不超过上限；任何一项不通过都会判 BAD，最后输出「总体: 有问题」并返回退出码 1。整个流程不生成 temp 目录：PCM 和静音帧都在内存里，只有试编码会临时用输出目录里的 `_trial.mp3`，跑完删除。

### output-chunks-duration.txt

每块的总时长，一行一个（秒，保留三位小数），包含前导静音——也就是这一块在整曲时间线上的结束时间。当前这首是：

```text
92.209
292.626
473.125
```

换行符固定 LF，最后一行后面没有多余空行，可以直接在 Scratch 里导入成列表（第 1 项对应 `1.mp3`，第 2 项对应 `2.mp3`……）。用 `--duration-file` 可以改输出位置。

### 音质和码率是怎么自动决定的

`MUSIC_BITRATE` 默认是 `auto`。编码前先用 ffprobe + 帧扫描看一眼输入：

- 输入是 **MP3**：CBR 用它的码率，VBR 用平均码率，取最接近的标准档。比如输入 320k → 输出 320k，输入 128k → 输出 128k。
- 输入**不是 MP3**（WAV/FLAC/ALAC 等无损格式，或 OGG 等）：统一用 320k（MP3 能给的最高档）。
- 想强制某个码率：`-b 320k` / `-b 192k`。

所以低码率输入不会再被 320k 白白撑大：128k 的整首只有 7.2 MiB，一块就装下了；同样这首 320k 要切 3 块。

注意：分块必须重新编码，所以码率跟输入一样也会多一代 MP3 损失。实测把 128k 源再编码成 128k，和源 PCM 的误差约 22 dB SNR（细听能分出比原文件糊一点）；再编码成 320k 则是 42 dB（基本透明），但体积是 2.5 倍。想尽量保音质、不在乎体积时，用 `-b 320k`。

另外两点没变：

- MP3 是有损格式，**不可能逐字节无损**。真正无损只能用 WAV/FLAC，而 60 秒立体声 WAV 就超过 10 MiB，会超过 8 MiB 的上传限制。
- 也没有采用「直接切原 MP3 字节」的写法：MP3 每帧都依赖前面的帧（比特池 + 合成滤波器），从中间硬切会让每块开头出现约 26 ms 的凹陷，那正是这个作品要避免的。重新编码一次是保证无缝的必要代价。

### 为什么静音几乎不占体积

前导静音会随着块序号越来越长：第 *n* 块要垫上前面所有块的总时长。如果这块静音也按音乐段的码率编码，越往后光静音就越接近 8 MiB（320k 时静音每分钟 2.4 MiB），后面的块就没地方装音乐了。

LAME 默认会跨帧共用比特（比特池），一帧的数据可能引用前面几帧的字节，这种流没法从中间替换帧。这里用 `-reservoir 0` 编码，使每一帧都自包含，于是可以把前面几分钟静音的帧整段换成 32 kbps 的静音帧：帧数不变，解码后的采样数和音乐起点也分毫不变，静音部分固定只按 32 kbps 算（每分钟约 0.23 MiB）。

### 为什么这样能无缝

MP3 每帧的频谱数据依赖前面几帧（比特池）。直接按字节切原 MP3，每块开头都会缺前文，产生约 26 ms 的凹陷。这里的每块都是从 PCM 独立编码出的新文件，第一帧不依赖任何前文；编码器把延迟/填充写进了 LAME 标签，解码器会自动裁掉，所以每块解码出来就是精确的 PCM 长度。

替换静音帧只发生在音乐开始之前（后面还留了至少 2 帧原编码的静音），而解码器在静音区的内部状态本来就是全零，所以无论换成什么样的低码率静音帧，音乐部分都逐采样不变。

### 在 Scratch 里怎么用

每块前面都垫了「前面所有块的总时长」的静音，因此可以把所有块**同时**开始播放：第 *n* 块要等前面几块播完才出声，任意时刻只有一块真正在响。这样就不依赖 Scratch 的定时器和「等待」精度，块与块之间也不会出现空隙。

按大小切块后块数不固定（这首 320k 是 3 块，128k 整首甚至只有 1 块），`.sb3` 里要放对应数量的声音和播放逻辑。换歌后重跑 `split.py`，看输出里的「共 N 块」，把 `.sb3` 的声音数量改成 N（文件名就是 `1.mp3` … `N.mp3`，和 Scratch 默认的声音编号一致），再用 `duration.py` 读出新的总时长填回 `计时器 < …` 判断；`.sb3` 里嵌的还是旧音频，需要把 `output-chunks/` 里的新文件重新导入。每块的时长在 `output-chunks-duration.txt` 里，可以直接在 Scratch 里导入成列表。

## duration.py

### 用途

看 `input.mp3` 有多长（秒），把输出的数字填到 `.sb3` 里——作品里用 `计时器 < 时长` 判断什么时候播完。

### 调用

```powershell
python duration.py                 # 默认读同目录的 input.mp3
python duration.py 别的文件.mp3     # 也可以读别的文件
```

输出秒数，保留三位小数，例如 `473.125`，直接抄进 `.sb3` 就行。

### 为什么不用 ffprobe 直接看

`ffprobe` 对没有时长索引的 MP3 会按首帧码率估算，可能差出好几秒。脚本会把它和「数 MPEG-1 Layer III 帧数 × 1152 / 采样率」的结果对一下，差超过 0.5 秒就用数帧的准确值，所以输出的数字可以直接用。

## 常见问题

- **`找不到源文件: …/input.mp3`**：确认源文件就叫 `input.mp3`，且和脚本在同一目录。
- **`命令失败: ffmpeg …`**：多半是 `ffmpeg` 不在 `PATH`，或输出文件被别的程序占用。
- **块数怎么不是 8 了？**：默认从后往前按 8 MiB 填满每块，块数由曲长和码率决定（这首 320k 是 3 块，128k 的整首 1 块就装下了）；最后几块是满的，第一块可能偏小。想固定每块 60 秒、切 8 块，用 `python split.py -s 60`。
- **为什么第一块比较小？**：默认从后往前填满，最后几块先占满 8 MiB，第一块是剩下的。这样前面块尽量短，静音总量和总体积最小。
- **音频超过半小时会怎样？**：这个「所有块同时播放」的方案里，第 *n* 块的静音 = 前面所有块的总时长，所以靠后的块光是静音就会逼近 8 MiB，脚本会报「曲目太长：靠后的块光是前导静音就会超过 8.0 MiB」。换成 `-s 60` 也一样，需要改用定时器触发下一块的播放方案。
- **输入是 128k 的 MP3，输出也会是 128k 吗？**：默认就是这样（`MUSIC_BITRATE = "auto"` 会按输入码率决定）。想不管输入、强制高码率就用 `python split.py -b 320k`。
- **输出目录会被清空吗？**：会。每次开始前会把整个输出目录删掉重建（子目录也会没），所以别用 `-o` 指向有其它文件的目录；指向项目目录或包含源文件的目录会直接报错。
- **`-s` 切出的块超过体积上限会怎样？**：校验会标 BAD，输出「总体: 有问题」，退出码 1。上限就是 `--max-size`（默认 8 MiB）；默认的按大小切块不会超过。
- **想省空间**：默认已经按输入码率编码，低码率输入不会白撑体积。想再小可以手动 `-b 192k`（音质会明显变差）。
- **想改每块上限 / 码率**：`python split.py --max-size 4M`、`-b 256k`；想按固定时长切就用 `-s 60`。参数表见上面的「调用」。
